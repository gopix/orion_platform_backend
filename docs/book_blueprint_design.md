## 2. The use case (as clarified)

Knowledge acquisition is done. Whatever documents were received are now vectors.
The next deliverable is the **Book Blueprint**: a title + an ordered set of
chapters (each with a summary and learning objectives), derived from the acquired
knowledge — **generated by the system, not typed by an end user**.

---

## 3. Agreed design (the approach we've settled on)

Route the blueprint through the **same RAG path** that later stages will use — so
retrieval is the single mechanism for the whole authoring pipeline.

```
project fields → templated query → embed → retrieve top-k chunks → LLM (RAG) → BookBlueprint → persist
```

1. **Templated query (system-generated, no human input).**
   Built from the project row, e.g.:
   > "Create a blueprint of the book titled '{book_title}' — subject:
   > {book_subject}, for {target_audience}. {book_description}"

2. **Embed** the query with `text-embedding-3-small` — the *same* model used at
   ingestion (required, or the vectors aren't comparable).

3. **Retrieve** from the `project_{id}` namespace.

4. **RAG-generate.** Hand the retrieved chunks + project metadata (notably
   `chapter_count`, `target_audience`) to the LLM, which drafts the structured
   blueprint.

5. **Persist** the blueprint.

### Key tuning insight (why retrieval params differ by stage)
A broad instruction like "create a blueprint for X" doesn't embed to anything
*specifically* similar to a given syllabus chunk, so similarity scores come back
low and flat. That's fine here: at the **blueprint** stage we want a *complete*
view of the syllabus (no unit dropped), so we set **`top_k` high and threshold
off** — retrieval is effectively "gather all the project's knowledge." Ranking
becomes meaningful *later*, at the **per-chapter** stage, where a specific query
("Thermodynamics: enthalpy, entropy") pulls a narrow, well-ranked slice.
→ Same retriever, two tunings.

## 4. Gaps in the current code (what actually needs building)

1. **`BlueprintGenerationAgent` ignores the documents.** Today it builds chapters
   from only `topic` + `audience`; it never reads the syllabus or interview. Core
   fix: feed it the retrieved knowledge.
2. **No endpoint runs it.** Need `POST /projects/{id}/blueprint`, parallel to
   `/process`.
3. **Nothing persists a blueprint.** The `book_forge_projects` table has
   `chapter_count` but nowhere to store the actual chapters.

Useful project fields already available for the template + steering:
`book_title`, `book_subject`, `book_description`, `target_audience`, `category`,
`chapter_count`, `expected_pages`, `primary_output_format`, `language_code`,
`book_status` (Draft → could advance to Blueprint).

## Decided

- **Route the blueprint through the RAG path** (templated query → embed →
  retrieve → LLM → blueprint). [Sec. 3]
- **Chapter schema (v1): flat, five core fields.** Each chapter:
  - `chapter_number` (int) — ordering
  - `title` (str)
  - `summary` (str) — paragraph describing scope
  - `learning_objectives` (list[str])
  - `covered_topics` (list[str]) — syllabus units the chapter maps to; also
    doubles as the retrieval query when generating that chapter's content later.
  No nested sections; no optional extras (`key_concepts`, `estimated_pages`,
  `difficulty_level`) in v1 — revisit at the content-generation stage.

  Blueprint (top level): `title`, `description`, `target_audience`,
  `chapters: [BlueprintChapter]`, `estimated_length`. Honors project
  `chapter_count`.

## 8. Senior review — authoritative direction (incorporated 2026-08-08)

Verified against the codebase; all of the following confirmed accurate.

**Reuse the existing architecture — do NOT build a new module or a standalone
service that bypasses LangGraph.** Everything needed already exists (Prompt
Engine, Embedding, Vector Store, LLM Service, Guardrails, Evaluation, LangGraph,
Blueprint agent + graph). We connect them.

### Entry path (thin, consistent with book_processing)
```
POST /projects/{project_id}/blueprint
  → AIWorkflowService.generate_blueprint()
  → BlueprintOrchestrator            (new, alongside book_processing_orchestrator)
  → GraphExecutionService("blueprint")
  → blueprint graph (already registered)
```

### Blueprint graph (already the right skeleton — fill it in, don't redesign)
```
START → retrieve_knowledge → generate_blueprint → review → approved? ─yes→ END
                                        ▲                         └─no→ generate_blueprint
```
- **retrieve_knowledge**: replace the STUB with real RAG — build templated query
  (PromptService) → embed (same model as ingestion) → `VectorStoreService.search`
  on `project_{id}` namespace → put chunks on state.
- **generate_blueprint**: use **PromptService** (versioned template), NOT an
  ad-hoc f-string. Feed project metadata + retrieved chunks → **LLMService** →
  JSON → **JsonRepair → Guardrail/schema validation** (not JsonRepair alone).
- **review**: ReviewAgent (already wired); Evaluation can plug in here later
  (syllabus coverage, grounding, completeness, audience alignment, hallucination).

### Prompt Engine (finally used here)
- Templated query includes `chapter_count` (part of query/context consistently).
- PromptService is **DB-backed** (`build_prompt_service(db)`, versioned templates)
  → PREREQUISITE: seed blueprint prompt templates (query + generation) into the
  prompts store; thread a `db` session to where prompts render.

### BlueprintState additions (RAG traceability)
Add: `chapter_count`, `query`, `retrieved_chunks`, `retrieval_metadata`.
Do NOT persist the raw embedding vector — query text + retrieved context are the
useful, traceable artifacts.

## 9. Revised decisions (supersede §5 where they conflict)

  retrieve stub. NOT a standalone bypass service. *(supersedes my earlier
  "focused blueprint_service" idea)*
- **Storage:** versioned **`book_forge_blueprints`** table —
  `id, project_id, version, title, description, blueprint_json, status,
  created_at, updated_at`. Chapters live inside `blueprint_json` (the flat
  five-field schema from §Decided). Keep version history across the review loop.
  *(supersedes the normalized `book_forge_chapters` table for v1)*

  `blueprint_json`.
- **Prompts:** via PromptService (versioned, DB-backed) — requires seeding
  templates.
- **Guardrails:** JsonRepair → schema/guardrail validation.

## 10. Senior review — round 2 (post first end-to-end run)

Verdict: functionally working, RAG architecture correct, do NOT rebuild — tighten.

**Done in this pass:**
- **Node → Agent consolidation.** The graph no longer calls inline
  `_retrieve_knowledge` / `_generate_blueprint` functions. It now uses
  `RetrieveKnowledgeNode` (retrieval) and `BlueprintNode → BlueprintGenerationAgent`
  (generation). The obsolete pre-RAG logic in `BlueprintGenerationAgent`
  (`f"Create a book blueprint about..."` + `_build_chapters` heuristic) is
  **deleted** — one generation path, not two.
- **Tightened `BLUEPRINT_SHAPE`** guardrail check to
  `{title, description, target_audience, estimated_length, chapters}`.
- **Whole-word toxicity match** (fixes "phosphate"→"hate", "skills"→"kill" false
  positives).
- **PolicyViolationException → HTTP 422** so a guardrail block is a clear,
  reported outcome, not a silent "failed".

**Deferred (agreed as later, not rebuilds):**
- [ ] **ReviewAgent → real editorial/syllabus evaluation** — currently structural
  only (has chapters? has objectives?). Should evaluate: required chapter count,
  syllabus/topic coverage, missing/duplicate topics, topic ordering, audience
  alignment, source grounding, SME coverage.
- [ ] **Full per-chapter schema validation** — the guardrail shape only checks
  top-level keys; a real contract should validate each chapter
  (`chapter_number, title, summary, covered_topics[], learning_objectives[]`).
- [ ] **Meaningful revision loop** — on "revise" the retrieved context is
  unchanged, so it's "try again". Later: route review feedback to either
  regenerate (generation problem) or gather more SME/documents (knowledge gap).
- Keep versioned persistence (confirmed valuable for the review/revision history).
